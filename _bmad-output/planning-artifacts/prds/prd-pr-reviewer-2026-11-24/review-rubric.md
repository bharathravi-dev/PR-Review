# PRD Quality Review — PR Reviewer (multi-channel automated PR validation)

*Calibration: open-source developer tool meant for adoption (not paid SaaS); fast-path draft whose `[ASSUMPTION]` tags the user accepted with "finalize it". Chain-top PRD, feeding UX, architecture, and stories.*

## Overall verdict
This is a strong PRD with a clear thesis: one engine reachable through four channels, bring your own AI, deterministic checks first, and honest status. It makes real decisions where the hard problems are: the per-channel subscription matrix (FR-10), polling with the user's own token for repos they don't administer (FR-26), and never approving or merging. It is ready to drive architecture for the Release 1 engine. The risks are concentrated in Auto-Review and in the "honest status" promise. Auto-Review has unmade product decisions with privacy, cost, and reliability consequences: which repo hosts the automation, and what posting as the user's own identity does to teammates. The status vocabulary is inconsistent at the exact points where honesty matters. The success metrics cannot be measured under the PRD's own no-telemetry stance. And more than half the FRs (mostly the Channel FRs) have no testable consequences, which is where story creation will struggle.

## Decision-readiness — adequate
Where the PRD decides something, it decides it well. FR-10's table names each subscription × channel combination with a reason. The Auto-Review grey area is resolved as "opt-in with warning", with a dated decision in OQ-1. FR-6 states the trade-off "AI-only findings cannot fail the Quality Gate by default". FR-13 closes the self-disabling-PR hole by reading repository configuration "from the PR's **base** branch". The Open Questions are genuinely open (OQ-2, OQ-3, OQ-4), and the market positioning in §1 cites its source.

What's missing is the consequences of the flagship Release 1 channel. The PRD decides *that* Auto-Review runs "entirely within the user's own GitHub account" (§4.6) but pushes the choices that determine whether it is safe and affordable into the addendum or into OQ-2. Similarly, "Publishes appear under the user's own GitHub identity by default" (FR-20) is treated as an identity setting, when it is really a social decision with visible effects on teammates. A reader pushing back on either point would find no acknowledgement.

### Findings
- **[high]** Auto-Review's hosting repo trade-off is unmade (§4.6 FR-26, FR-28; §9 OQ-2; addendum B3) — The setup command "creates the automation in their own GitHub account" with a schedule and "a state file … in the automation repo". Whether that repo is public or private decides three product outcomes, and the PRD names none of them. **Private:** polling every 15 minutes (FR-28 default) is about 2,880 job-runs a month. Actions bills each job rounded up to the minute, so polling alone can exceed GitHub Free's 2,000 private-repo minutes before any deterministic layer runs (verify current quotas). **Public:** minutes are free, but run logs and the state file expose PR references, and possibly findings, from private org repos the user reviewed. GitHub also disables scheduled workflows in public repos after 60 days without repository activity, so Auto-Review stops silently, and FR-29 "visible health" cannot report it because nothing runs. *Fix:* Add an FR that fixes the automation repo's visibility (or makes it an informed setup choice), says what may be written to logs and state there (no finding text or code for private targets), and requires a keep-alive or a staleness signal outside the workflow. Restate OQ-2 with the quota arithmetic and choose a default poll interval that fits the free tier.
- **[high]** Posting as the user has unexamined consequences for teammates (FR-20, UJ-2, §2.1 Social JTBD, FR-27) — UJ-2 promises that whenever Arjun "is requested as a reviewer anywhere, a review appears on that PR under his name". On GitHub, a submitted review of any type from a requested reviewer normally clears that review request (verify). Teammates would then see Arjun's request satisfied by a machine review he never read: the opposite of the Emotional JTBD "don't be the reviewer who approved the PR that broke production". The PRD also never says whether published reviews disclose that they are automated, which the Social JTBD ("read as helpful rather than as bot noise") depends on. *Fix:* Add consequences to FR-17/FR-20: every Published summary carries a visible "automated review by PR Reviewer (provider/model)" marker. Then decide and state whether Auto-Review on review-requested PRs posts a review (which clears the request), posts a plain comment (which doesn't), or leaves it to configuration.
- **[medium]** The subscription matrix contradicts the CLI-companion backend (FR-10 table vs FR-37, UJ-4) — FR-10 marks Claude and ChatGPT subscriptions "Not available" for the Browser Extension. But FR-37 lets the extension drive "a local CLI companion running on their machine", which is the CLI channel where those subscriptions are "Allowed". Either the companion inherits CLI permissions, and the table is wrong, or there is a vendor-terms reason it differs, and the PRD doesn't give it. *Fix:* Split the Extension column into "via Web App" and "via local CLI companion", and give the rule for each.
- **[medium]** The Web App privacy model conflicts with its team use case (FR-30, FR-34 vs UJ-3) — UJ-3 is "Meera gives her team a review page", and "past reviews stay listed per PR". But FR-30 says "Each user's Credentials and Reports are private to them", so teammates cannot see each other's runs on the same PR, and FR-34's history is per user. With OQ-4 also open, a team can produce N independent summaries per PR. *Fix:* Decide whether Reports are private, shared per instance, or shared per repo for users with read access, and make FR-34 match.

## Substance over theater — strong
Nothing here is furniture. All four UJs have named protagonists with a concrete constraint that drives a decision. Arjun "can't install apps there" drives polling (FR-26). Meera self-hosts, which drives FR-35 and the one-command NFR. Tom's "isn't connected to a backend yet" drives FR-37. Anika's existing Claude Code drives FR-10/FR-16. The Vision is specific to this product: "a reviewer that quietly checks every PR you open or are asked to review — including in organisations where you can't install anything" could not be swapped into a competitor's PRD. Differentiation is grounded in research, including honest out-of-scope items (GitHub Models retired, Copilot has no sanctioned route). The NFRs carry numbers (NFR-5: "≤ 30 changed files, ≤ 1,500 changed lines … ≤ 3 minutes … ≤ 10 minutes"), and the security NFRs are tied to testable FR consequences (FR-15's fake-key injection test, FR-39's credential-reading install script). No findings.

## Strategic coherence — adequate
The thesis is explicit (§1 "Why this, given what exists"), and the features follow it. The engine is shared (§4.1), providers are pluggable (§4.2), configuration contains no hardcoded values (§4.3, enforced by FR-1's repo scan), and each channel maps to one UJ. Counter-metrics exist and are well chosen (SM-C1, SM-C2). Release order follows "closest to today's tool" (§6.1), which is a defensible platform-MVP logic.

Two things weaken the arc. First, the "deterministic-first" half of the thesis may not reach the default user. Second, the success metrics cannot be observed as written.

### Findings
- **[high]** The no-sandbox default experience is unstated and probably close to AI-only (§1 Vision, UJ-1, FR-39, FR-40) — The Vision promises to "run the checks that can be run deterministically (compile, lint, tests, static analysis)". FR-39 runs none of them without a container runtime, so a CLI user without Docker gets `SKIPPED (no sandbox available)` for compile, lint, and tests. FR-40 tries to keep "repo lint configs via static parsing where the tool supports it". But common lint setups (ESLint flat config `eslint.config.js`, plugin resolution from `node_modules`) execute repository code to load, so "where the tool supports it" may be almost nowhere for the v1 JS/TS validators. UJ-1, the CLI journey, never shows Anika what she loses without Docker. If most laptop runs are AI plus secret scanning, the honest-status thesis still holds, but the "deterministic-first" pitch does not. *Fix:* In UJ-1 or §4.9, state what a no-sandbox CLI run delivers (which layers run, which are SKIPPED, and FR-5 CI-result reuse as the main substitute). Narrow FR-40 to layers that need no tool that loads repo config (syntax parse, secret scan, AI). Consider whether setup should recommend installing a container runtime.
- **[high]** The success metrics cannot be measured under the PRD's own constraints (§8 SM-1–SM-6 vs NFR-3) — NFR-3 says "No telemetry by default". SM-1 (resolved share), SM-2 (dismissed share), SM-5 (setup within 10 min), and SM-6 (provider share of runs) all need cross-user run data. The `[NOTE FOR PM]` covers only SM-1/SM-2. SM-2 also needs a way to "mark wrong", and no FR provides one: there is no feedback or reaction mechanism on Findings. Only SM-4 (npm downloads, which are public) is observable as is, and it measures activity rather than the thesis. *Fix:* Add a measurement plan per SM. For example: a maintainer dogfood cohort measured directly from GitHub, proxies that need no telemetry (resolved-finding counts from FR-19's resolution marking, reactions on bot comments), and a specified opt-in telemetry event set. Add a small FR for marking a Finding as wrong (e.g. a reaction or reply convention that FR-19 reads on re-review).
- **[medium]** SM-3's target conflicts with FR-28 and NFR-5 (SM-3, FR-28, NFR-5) — The SM-3 target is a median of ≤ 15 minutes from PR open to published review. With the default poll interval of "≤ 15 minutes" (an average wait of about 7.5 min), plus NFR-5's run time of 3–10 min, plus scheduled-workflow start delays, the median is around 11–20 min. The default configuration may not meet the PRD's own target. *Fix:* Set the target from the arithmetic (e.g. ≤ 20 min median at the default interval), or tighten the default interval and accept its cost (see the hosting-repo finding).
- **[medium]** Release 1 breadth has no de-scope lever (§6.1) — Release 1 includes the engine, all nine providers (each with a conformance suite, FR-9, which needs Azure and Bedrock accounts in CI), CLI, Auto-Review, deterministic validators for five ecosystems, a Sandbox, SonarQube/CI reuse, and secret and dependency scanning. Releases 2 and 3 are also labelled "v1", so "v1" means three releases. For a solo open-source maintainer, the PRD doesn't say what ships first if Release 1 slips. The user did choose "all providers at first release", so this is a sequencing gap rather than an override. *Fix:* Rename the releases or the version (e.g. v1.0 = Release 1). Within Release 1, mark a cut line (for example: Anthropic API + Claude subscription + OpenAI-compatible adapter first, and the other providers as fast-follow within R1).

## Done-ness clarity — thin
The engine FRs are mostly well specified. FR-1, FR-4, FR-6, FR-13, FR-15, FR-17, FR-19, and FR-39 have sharp, testable consequences ("Running the same review twice leaves exactly one summary on the PR"; "A test PR whose install script tries to read environment Credentials finds none"), and depth is delegated to the Validation Capability Spec. Done-ness falls off sharply after §4.4. Only 14 of 40 FRs carry a Consequences block. Most of the 26 that don't are Channel FRs (FR-22–FR-37), and story creation will lean on those hardest. The status vocabulary, which carries the "honest status" promise, is inconsistent.

### Findings
- **[high]** The honest-status vocabulary is inconsistent where it matters most (Glossary "Layer Status" and "Review Run"; §4.9; FR-4; FR-12; FR-39; UJ-3) — The Glossary defines seven Layer Statuses and no others. Then §4.9 says layers without a Sandbox are "reported `unavailable`", FR-39 says `SKIPPED (no sandbox available)`, and FR-12 and UJ-3 mark the AI layer "`incomplete`", which is a Quality Gate status, not a Layer Status. FR-4 says a missing mandatory layer makes the gate "`INCOMPLETE` or `FAILED`" without saying which, or that the choice is policy-driven (Spec §26 `failClosedWhenRequiredChecksUnavailable`). The Glossary says a Review Run "has an overall status (see §4.1)", but §4.1 only defines Quality Gate outcomes, and FR-17 lists "overall status" and "Quality Gate result" as separate summary items. An engineer cannot tell how many status fields a Report has, or what an exhausted cost ceiling (FR-12) or a rate-limited provider (UJ-3) should produce. *Fix:* Map each case to an existing Layer Status (e.g. no sandbox → `SKIPPED` with reason; cost ceiling or rate limit → `ERROR` or `TIMEOUT` with reason). State whether Run status and Quality Gate result are one field or two. Make FR-4's INCOMPLETE-vs-FAILED choice explicitly governed by Quality Gate configuration.
- **[high]** Over half the FRs have no testable consequence, concentrated in the Channels (FR-11, FR-14, FR-16, FR-24, FR-25, FR-27, FR-29–FR-37) — The specific gaps:
  - FR-14: "Rules are checked on every run": what does "checked" mean for prose rules, who judges compliance (the AI layer?), and can a rule fail the gate?
  - FR-11: does fallback switch providers mid-run (mixing AI Findings from two models), and may it fall from a Subscription Provider to a paid API key without telling the user?
  - FR-16: what is the minimum set setup requires (GitHub Credential plus one AI Provider?), and what happens when a test call fails?
  - FR-24: "documented exit codes" with no mapping.
  - FR-25: "list and pick" with no filter or interaction spec.
  - FR-29: "optionally a notification" without saying which channel.
  - FR-31–FR-36: no performance, failure, or concurrency bounds for the Web App or Extension.

  *Fix:* Add one to three Consequences per FR. For FR-24, include the exit-code table. For the engine, adopt Validation Capability Spec §36's acceptance table as the engine's acceptance criteria, marking which rows are v1 (see the Downstream finding).
- **[medium]** The local CLI companion is load-bearing but undefined (FR-37, UJ-4, §6.1) — It appears in UJ-4, FR-37, and §6.1 ("reusing the Web App backend and the CLI companion"), but no CLI FR (§4.5) defines it. It would be a localhost service holding the GitHub write Credential and accepting review and Publish requests from a browser, a security surface (cross-origin requests, DNS rebinding, any local page calling it) that NFR-1/NFR-2 do not cover. *Fix:* Add a CLI FR for companion mode covering opt-in start, loopback-only binding, pairing or authentication with the extension (e.g. extension-ID allow-list plus a token), and which actions it exposes. Add the term to the Glossary.
- **[medium]** "Source code is not retained" conflicts with stored Reports (NFR-10 vs FR-32, FR-34) — Reports include "evidence and code context" (FR-32), and the Web App keeps them as history (FR-34). Code snippets therefore persist by design, contradicting NFR-10's "Source code is not retained after the run unless the user opts in". *Fix:* Define what "source code" excludes (snippets inside Findings) or give a retention and limit rule for code context in stored Reports.
- **[low]** `REQUEST_CHANGES` cannot be used on the user's own PRs (FR-18, FR-27) — Watch Scope includes "PRs they authored". GitHub does not allow requesting changes on your own PR, so an enabled `REQUEST_CHANGES` fails there. *Fix:* Add a consequence: on self-authored PRs, always publish `COMMENT`.
- **[low]** Edited Findings vs fingerprints (FR-33, FR-19) — Users can "edit Findings before Publishing", but it is unspecified whether an edited Finding keeps its fingerprint for resolved/unchanged tracking. *Fix:* State that edits change the published text only; the fingerprint is preserved.

## Scope honesty — adequate
Omissions are explicit. §6.2 and §7 do real work ("does not resell AI usage or proxy users' Credentials", "not a replacement for CI, SonarQube, or human review"), FR-9 lists out-of-scope providers with reasons, and §2.2 names non-users. The open-items density is 26 inline `[ASSUMPTION]` tags, 7 Open Questions, and 1 `[NOTE FOR PM]`. That is high, but acceptable for an open-source tool at launch-lite stakes, given the user explicitly accepted the assumptions. The remaining problem is that the document no longer says which of those items are settled.

### Findings
- **[medium]** The status of accepted assumptions is ambiguous after "finalize" (§6.1, §10, front matter, title) — The user accepted the assumptions, but the PRD still says "`[ASSUMPTION: v1 cut and release order — user said "assume"; confirm]`" (§6.1), "*Working title — confirm.*" (title), and `status: draft` (front matter). Downstream workflows can't tell whether the release order, NFR-5 targets, or FR-37's dual backend are decisions or placeholders. *Fix:* Mark index entries as "accepted 2026-11-24" (keep the tags for traceability), remove "confirm" wording from accepted items, update `status`, and keep only genuinely open items as Open Questions.
- **[medium]** Org data governance is silent (§4.6, FR-27, NFR-3, §7) — Watch Scope (d) reviews "PRs in listed orgs or repositories they don't administer". This sends private org code to the user's personal runner and the user's chosen AI Provider, which many orgs' policies restrict. The PRD neither states this as the user's responsibility nor adds friction (e.g. a confirmation per org at setup). For a tool whose differentiator is working where you "can't install anything", that omission will be read as endorsement. *Fix:* Add a Non-Goal or an FR-27 consequence: enabling an org the user doesn't administer shows a one-time notice that the org's code goes to the configured AI Provider and the user's own runner, and the PRD does not enforce org policy.

## Downstream usability — adequate
The Glossary is strong: it is capitalised, precise, and distinguishes infrastructure failure from validation failure under "Layer Status". The IDs are contiguous and unique (FR-1–40, NFR-1–10, UJ-1–4, SM-1–6, SM-C1–C2). Every Validation Capability Spec section cited (§5, §6/§6.1, §7, §9.9, §10.3, §20.3, §21, §22, §23–§26, §28, §29, §32, §33, §34) exists in `additional_info.md`. Each UJ has a named protagonist. The weak points are the status drift above and the PRD's relationship to the spec.

### Findings
- **[medium]** There is no precedence rule or acceptance mapping against the Validation Capability Spec (§0, §6, Spec §36–§37) — §0 says the PRD "builds on, and does not duplicate" the spec, but never says which document wins on conflict. The spec is written as implementer instructions, with its own acceptance criteria (§36, including "SonarQube gate fails" and Node.js validation) and implementation phases (§37, including a SonarQube scanner phase). Those partly conflict with PRD §6 (SonarQube reuse only, a narrower v1 validator set). Story creation will pull from both. *Fix:* Add to §0: "Where the spec and this PRD conflict, this PRD governs; spec §37 phases are superseded by §6." Add a short table marking spec §36 rows as v1 / deferred.

## Shape fit — strong
A multi-channel developer tool with distinct users per channel suits the UJ-plus-capability-spec shape. The four UJs are each one channel's acceptance story, not decoration. Delegating validation depth to the external spec keeps the PRD at product altitude, and pushing mechanisms (polling queries, MV3 storage, `claude -p`/`codex exec`) to the addendum is the right split for a chain-top PRD. Brownfield context is handled in addendum §A, with specific items to remove (`rules/sunbird-cb-portal.md`) and one explicit current-vs-required delta inline (FR-39: "Today's workflow runs them in one process; this must change"). No findings.

## Mechanical notes
- **Status-term drift:** `unavailable` (§4.9), `incomplete` (FR-12, UJ-3), and `SKIPPED (no sandbox available)` (FR-39) are used for Layer Status values that the Glossary doesn't define. See the Done-ness high finding.
- **Undefined terms:** "CLI companion" and "backend" (FR-37, §4.8, §6.1) are not in the Glossary. The AI layer is called "AI Validation Layers" (§4.2), "AI layer" (FR-6, FR-12), and "AI contextual review" (FR-3 Glossary example, §6.1). Pick one term.
- **Glossary cross-reference:** "Review Run — Has an overall status (see §4.1)": §4.1 defines Quality Gate outcomes, not a run status.
- **Assumptions Index roundtrip:** all 26 inline tags map to the 21 index entries (some entries combine tags). 13 inline tags are bare `[ASSUMPTION]` with no inline text (FR-12, FR-20, FR-26, FR-30, §4.7 ×2, §4.8, NFR-3, NFR-5, NFR-6, NFR-9, SM-1/2/4), so a section pulled out alone loses what was assumed. Consider inlining short text.
- **Redundancy:** NFR-6 restates FR-22's platform and Node LTS support. FR-9's "Adding another provider requires only a new provider adapter" restates NFR-7.
- **Front matter:** `status: draft` and "*Working title — confirm.*" persist after the user's "finalize".
- **Dated external facts** (Claude usage credit 2026-06, GitHub Models retirement, Files-changed redesign) are appropriately flagged "re-check at release" in FR-10 and OQ-1. Keep that pattern for the GitHub Actions quota and schedule facts this review relies on.
