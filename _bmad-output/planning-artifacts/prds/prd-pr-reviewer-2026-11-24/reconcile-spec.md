# Reconciliation: PRD vs Validation Capability Spec

**What this checks.** It looks for spec requirements that the PRD either (a) drops silently, meaning no FR or NFR covers them, no explicit `(Validation Capability Spec §N)` reference hands them to the spec, and §6.2 does not defer them, or (b) contradicts. Restating the spec is not required.

**How coverage is labelled.**
- **FR-n / NFR-n**: the PRD covers it directly.
- **delegated via §ref**: a PRD item cites that spec section. §4.1's blanket "§5–§26 are not restated" counts as delegating §5–§26 only.
- **deferred §6.2**: the PRD defers it explicitly. The blanket line "Full L1–L14 deterministic coverage … added incrementally" counts as deferring per-technology deterministic depth.
- **GAP / CONFLICT**: rated (high / med / low).

**What is delegated and what is not.** §31, §35, §36 and §39 sit outside the §5–§26 blanket, and no FR cites them, so none of them is delegated. §27.1 is also not delegated, because FR-17 cites no spec section.

## 1. Summary of material issues

| # | Issue | Spec | Severity |
|---|---|---|---|
| 1 | Subscription Providers are agent CLIs (Claude Code, Codex) that come with file, shell and network tools, and the PRD sets no tool-permission limit on them. Prompt injection could then lead to code execution, repo-wide reads, or the AI posting to GitHub through a logged-in `gh`. | §30, §29, §39 | high |
| 2 | Secret values in PR code are sent to the AI provider. NFR-2 covers only reports and the product's own Credentials, and NFR-3 says PR code goes to the provider, with no redaction step. | §13 (spec:1236), §29 | high |
| 3 | Repository configuration sits above user configuration, and nothing limits which keys a repo config may set (provider or base URL, Rules URL, `REQUEST_CHANGES`, enabling execution). An untrusted repo could redirect the user's API key or code, or change what is published under the user's name. | §29 "separate trusted tool config", §34 | high |
| 4 | Nothing defines which layers are mandatory by default. With FR-4 (a mandatory layer that did not run → INCOMPLETE) and FR-39 (no sandbox → SKIPPED), every run on a laptop without Docker may end INCOMPLETE. "Skipped by design" is left unresolved (extract D.14). | §26, §33, §36 | high |
| 5 | Incremental review across commits is under-specified. Nothing prevents re-posting unchanged findings inline on every push. "Re-review only what changed" (UJ-2) has no FR saying how the gate still reflects the whole PR. When posting as the user (FR-20), "own summary" and "human comments" cannot be told apart without a marker. | §28 | med-high |
| 6 | The PRD uses statuses outside the spec's enum: the AI layer "`incomplete`" (FR-12, UJ-3) and layers "`unavailable`" (§4.9). | §33 | med |
| 7 | Backward compatibility and migration for the existing `review.mjs` CLI flags, workflow, `rules/<repo>.md` resolution, `--dry-run` and the severity scale are never addressed. "Never modifies PR code" is missing from Non-Goals. | §3, §39, §38 #24 | med |
| 8 | Caching, cache-key composition and cross-repo or cross-user cache isolation are absent. So are validator timeouts and bounded concurrency. | §31, §28 | med |
| 9 | §35 platform tests and §36 acceptance criteria are not adopted or scoped for v1. Some §36 rows (Java static analysis, Python security) cannot pass with the v1 validator set, and the PRD does not say so. | §35, §36 | med |
