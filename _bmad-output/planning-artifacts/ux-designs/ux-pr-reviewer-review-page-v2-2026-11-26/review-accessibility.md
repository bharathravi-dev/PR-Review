# Accessibility Review — pr-reviewer review page v2

Reviewed: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, `mockups/key-start.html`, `mockups/key-v2.html`, `mockups/key-post-edit.html`, against the sibling `../ux-pr-reviewer-2026-11-26/EXPERIENCE.md` (Accessibility Floor) and `DESIGN.md` (contrast table, focus ring). Target: WCAG 2.1 AA. Ratios computed with the WCAG 2.x relative-luminance formula from the hex values in `DESIGN.md`.

## Verdict

**Not ready for stories.** The palette holds up: every text pair in `DESIGN.md` passes 4.5:1 in light and dark, including the new v2 tokens (sidebar, accent-soft, diff backgrounds, toast). The failures are behavioural. The spine leaves its main interaction pattern open, and the option it offers first (a listbox whose rows contain real checkboxes) is invalid ARIA. The single-key shortcut guard is too narrow: `c`, `x` and `p` will fire while someone types in the review-type select or the palette. Esc does five jobs with no order of precedence, and one of those jobs throws away an edit. Toast actions can't be reached by keyboard within 8 seconds. Forced colours aren't mentioned, and the selection indicators are built entirely from things forced colours removes. The claim to inherit the extension's floor is nominal: v2 inherits only "announcement and time-limit rules", and the extension's time-limit rules cover pairing codes, which v2 doesn't have. Most of that floor (focus fallback, aria-disabled reasons, step state words, forced colours, the two-tone focus ring) isn't inherited. Two mockup defects would ship if copied as drawn: white-on-white `kbd` keys inside primary buttons (1.00:1), and an active state on the icon rail that's shown by hue alone.

## Findings

### Critical

- **[critical] The list pattern isn't decided, and the first option is invalid** (EXPERIENCE.md, Accessibility Floor bullet 3: "listbox-like single tab stop … `aria-activedescendant`, or plain buttons in DOM order; the checkbox stays a real checkbox"). A `role="option"` must not contain interactive descendants. With `aria-activedescendant`, DOM focus stays on the listbox, so the "real checkbox" can never take focus, its state isn't announced as a checkbox, and NVDA/JAWS will flatten or ignore it. A listbox also models only one state, but each row has two: which finding is *shown* and whether it's *included*. Leaving the choice open means two developers will build two different, incompatible things. *Fix:* replace the bullet with: "The finding list is a `<ul>` (labelled with the surface name and count). Each `<li>` holds, in order, a native `<input type="checkbox">` labelled 'Include in post: <SEVERITY> <title>, <path>:<lines>' (the label wraps the checkbox column for a ≥24px target), then a `<button>` with the title as its name and `aria-current="true"` on the finding shown in the detail. No listbox, no `aria-activedescendant`, no `role="application"`. j/k and ↓/↑ (when focus is in the list) move focus to the next or previous row's title button and show it in the detail. `x` toggles the checkbox of the focused or shown row. Severity badge text is part of the button's name, or is its description via `aria-describedby`." If single-tab-stop is required, commit to an APG `grid` instead (row per finding; checkbox cell and title cell; roving `tabindex`; ←/→ between cells; Space toggles, Enter opens) and write that key map into the spine. Don't use a listbox with checkboxes.

- **[critical] The single-key shortcut guard is too narrow; shortcuts will fire while people type** (EXPERIENCE.md, Interaction Primitives: "act only when focus is not in a text field"). Some controls take letter keys but aren't text fields: the drawer's review-type `<select>` (typeahead: "c" for Comment also triggers *Copy agent prompt*), the palette's combobox and its options, native checkboxes and buttons inside the open drawer, `contenteditable`, a pending IME composition, and macOS dead keys (Option+e). `x` (exclude) and `p` (open drawer) change state, so a stray keystroke is a silent data change. Modifier combinations aren't excluded either (Ctrl+C would run `c`). *Fix:* add to Interaction Primitives: "Single-key and `g`-chord shortcuts are ignored when: focus is in `input`, `textarea`, `select`, `[contenteditable]`, or any element with role `combobox`, `textbox`, `searchbox`, `spinbutton`, `slider`, `listbox`, `menu`, `menuitem*`, `option`, `grid`-cell editors; `event.isComposing` is true; any of Ctrl/Alt/Meta is held (Shift only for `?`); or any dialog (palette, drawer, `?` sheet, Settings) is open, in which case only that dialog's own keys work. `x`, `e`, `c` act on the shown finding only when focus is in the list or detail region (WCAG 2.1.4 'active only on focus' as the default); `g` chords, `?`, `/` and `p` are page-wide." Also: "Every control with a shortcut has `aria-keyshortcuts`. Never use `role="application"`; screen-reader browse-mode quick keys (h, e, c, x, k, g, p in NVDA/JAWS) take precedence, and every shortcut has a visible control that does the same thing."

### High

- **[high] The inheritance from the extension's Accessibility Floor is nominal** (EXPERIENCE.md, Foundation para 2: inherits "the Accessibility Floor's announcement and time-limit rules"). The extension's time-limit rules are about pairing-code expiry, which v2 doesn't have, so nothing covers toast timing. v2 doesn't inherit, and doesn't restate: focus falling back to the `h1` when the focused element disappears on an automatic change; `h1` with `tabindex="-1"`; dialog initial focus; `aria-disabled` plus a described reason for disabled actions ("reviewing is off with the reason" / "posting off" are stated visually only); state words on steps (Waiting / Running / Done / Failed / Skipped); path-link accessible names; Settings form errors (`aria-invalid`, focus to first failed field); forced colours; the two-tone focus ring (`focus-ring-outer`/`-inner` exist in the extension's DESIGN.md but not here). *Fix:* change the sentence to "inherits the extension's Accessibility Floor in full (Structure, Focus, Announcements, Controls and content, Motion/zoom/forced colours); this section lists only v2's additions and overrides". Then add the items in H3–H6 and H11 below, and add `focus-ring-outer` and `focus-ring-inner` to v2's `colors`.

- **[high] Esc has five meanings, no order of precedence, and one of them destroys work** (EXPERIENCE.md, Interaction Primitives and Inline editor: "Cancel (Esc) restores"). Esc closes the palette, closes the drawer, cancels the editor, goes back on narrow screens, and must also dismiss tooltips on the icon rail (WCAG 1.4.13). At under 800px with the editor open, one Esc could cancel the edit and a second could leave the finding. JAWS (and NVDA's focus mode) users routinely press Esc to leave forms mode, so an Esc that discards a reworded comment is a data-loss trap. *Fix:* add "Esc precedence, innermost first, one layer per press: open tooltip → native select/menu/autocomplete popup → palette → `?` sheet → post drawer → inline editor → list filter text (clears) → narrow detail (back). In the inline editor, Esc with unsaved changes keeps the draft and moves focus to the Cancel button with 'Unsaved changes. Press Cancel to discard, or Save.' announced; only the Cancel button discards. Esc never navigates while a text field has content."

- **[high] Toasts: 8s auto-dismiss, an action keyboard users can't reach, and error toasts that vanish** (EXPERIENCE.md, Toast row; DESIGN.md, Toast). A keyboard user deep in the list can't Tab to a bottom-right toast inside 8s, and "unless hovered or focused" doesn't help them get there. 2.2.1 requires that time limits be turnable off, adjustable or extendable; pausing on hover isn't any of those. Errors "that need action" announced via `role="alert"` that then disappear leave no trace. Toasts can also cover the focused post bar or Post button (2.4.11 in WCAG 2.2). *Fix:* "Toasts never take focus. Info toasts dismiss after 8s, and the timer runs only while the page is visible and focused (`visibilitychange`). Error toasts and any toast whose action has no other route don't dismiss automatically, and have a Close button. Settings has 'Keep notifications until dismissed'. F6 (and the palette command 'Go to notifications') moves focus to the newest toast. Every toast action is also reachable without the toast (Show = `g a`; Retry is on the surface). The toast region is placed so it never covers the focused element; the drawer and post bar get bottom padding equal to the stack height. The action label makes sense on its own ('Show findings', not 'Show'). The status region speaks the toast text once; when the toast duplicates the run-result announcement, only one is spoken."

- **[high] The single-colour focus ring fails on the toast and on accent fills** (DESIGN.md, `focus: #2f5bd3` / `focus-dark: #7c9cf5`). Focus on toast-bg is 2.74:1 (light) and 2.13:1 (dark). A focus ring touching a primary button or a checked checkbox is 1.00:1. No outline width or offset is specified. *Fix:* in DESIGN.md `colors`, add `focus-ring-outer: '#1c2128'`, `focus-ring-inner: '#ffffff'` and the dark pair (`#e3e7ec` / `#0f1216`). Add a `focus` component: "2px solid {colors.focus} outline, 2px offset, on every focusable element; on the toast, the primary button, and anything on an accent fill, use the two-tone ring (2px {colors.focus-ring-outer} outline + 2px {colors.focus-ring-inner} inner ring), ≥3:1 against every background in this file." Implement the ring as `outline`, not `box-shadow`, so it survives forced colours.

- **[high] Forced colours: the selected row and active nav vanish** (DESIGN.md, `nav-item-active`, `finding-row.selected`; not mentioned anywhere in v2). Selection is drawn as a background plus `box-shadow: inset 2px 0 0 accent`. Forced-colours mode removes both. The mocked checkbox is a styled `<span>`, so it disappears. The diff tints go too. The toast has no border, only a shadow and a background, so it merges with the page. The why-box loses its fill. *Fix:* add to the Accessibility Floor: "Forced colours: selection and active indicators use a real `border-left: 2px solid` (mapped to `Highlight`), not `box-shadow`; checkboxes are native (`accent-color`); toast, why-box, suggestion box, tiles and drawer keep a 1px border (`CanvasText`); focus uses `outline` (`Highlight`); the diff's change type is visible as a `+`/`−` gutter column and the selected or current state is also in text (`aria-current` plus a visually hidden 'shown')." In DESIGN.md `nav-item-active.indicator` and `finding-row.selected`, change "2px inset left" to "2px left border".

- **[high] Several states are shown by colour alone** (key-v2.html frames 1, 3, 5; DESIGN.md `run-timeline`, `filter-chip.active`). Done-OK and done-with-warnings timeline nodes differ only by dot hue ("Lint · TSLint" with a warn dot). The waiting node is `border` at 1.31:1. The active icon on the icon rail is an accent glyph on accent-soft against muted glyphs on the sidebar: 1.02:1 between the two glyph colours and 1.02:1 between the fills in light, with no indicator bar. The active filter chip differs from an inactive one mostly by hue (accent vs muted text, 1.02:1). The identity line shows health only with "● " in ok colour. *Fix:* run-timeline: "each node has a state word in text (Waiting, Running, Done, Done with warnings, Failed, Skipped) before its outcome; the dot is `aria-hidden`; the waiting node is a 9px ring in {colors.border-strong} (3.64/3.76:1)". Rail: "the active icon gets the same 2px left indicator as `nav-item-active`, plus `aria-current="page"`". Filter chip: "active chips are toggle buttons with `aria-pressed="true"` and a leading ✓ glyph, plus the accent border". Identity: "health in words ('GitHub: signed in as @x', 'AI: claude-code ready')".

- **[high] Focus management across the three panes isn't specified** (EXPERIENCE.md, Accessibility Floor bullet 2 covers only surface changes and closing overlays). Several questions are open. Do j/k move focus or only the detail? Does Enter move focus into the detail? How does a keyboard user get from sidebar to list to detail without tabbing through about 15 sidebar items? Where does focus go when the selected row is filtered out, when `x` on the Pre-existing surface moves the row, when narrow back returns, or when a focused skeleton tile is replaced as a run finishes? *Fix:* add "Focus model: DOM and Tab order is sidebar → list → detail. F6 / Shift+F6 cycle the sidebar, list, detail and notifications regions, and a skip link 'Skip to findings' is first in the page. j/k and ↓/↑ move focus between list rows and update the detail without moving focus. Enter (or activating the title) moves focus to the detail's finding heading (`h2`, `tabindex="-1"`). On narrow screens the detail replaces the list: focus goes to the finding heading, and back (Esc / '← Needs attention') returns focus to that finding's row. If the focused row is filtered out or removed, focus goes to the nearest following row, else the previous, else the list heading; this is announced ('Showing 1 of 2'). When a run finishes, any element that has focus and still exists keeps it; replaced tiles keep their DOM node, so skeleton→value is an in-place update; otherwise focus goes to the surface `h1` (inherited rule). A finished run never switches surface on its own if the user has navigated since starting it."

- **[high] The post drawer can't be closed except with Esc; modal behaviour and narrow width aren't specified** (key-post-edit.html frame 2 shows only a `kbd Esc` in the heading; EXPERIENCE.md Post drawer row). Mouse, touch and switch users have no way out. The spec says focus is trapped but not that the rest of the page is inert. Initial focus isn't given. A 480px drawer over a 320px viewport isn't addressed. Behaviour when ⌘K, j/k or `p` is pressed while it's open isn't defined. *Fix:* "The drawer is a modal dialog (`<dialog>` opened with `showModal()`, or `role="dialog" aria-modal="true"` with the rest of the page `inert`), named by its heading 'Post to GitHub'. It has a visible Close button (≥24px, accessible name 'Close'). Initial focus goes to the heading (`tabindex="-1"`) while the preview builds; 'Preview ready: 2 inline comments and the summary' is announced; focus never lands on Post automatically. Below 800px it is full-width (`width: min(480px, 100vw)`). While it is open, ⌘K and page shortcuts are ignored. After a successful post, focus moves to the result line, which has `tabindex="-1"`. Close returns focus to the invoker (the 'Preview post' button, or the list row if `p` was pressed there)." Apply the same Close button and `width: min(640px, 100vw - 32px)` to the palette.

- **[high] Animation over 5 seconds needs a pause control even without a reduced-motion preference** (EXPERIENCE.md Run timeline: "a running node animates (static under reduced motion)"; Accessibility Floor last bullet). The running ring turns for the whole AI step (52s in the mockup), alongside other content. WCAG 2.2.2 (Level A) requires pause, stop or hide for any motion that starts automatically and lasts over 5s, whatever the OS setting. The ticking elapsed time ("0:41") is auto-updating content under the same criterion. Skeleton shimmer isn't specified either way. *Fix:* "The running ring animates for at most 5s, then stays static; 'Running' is the state word. Skeletons don't shimmer. Elapsed time updates every 10s or less often, and is not a live region. Under `prefers-reduced-motion: reduce`, there are no transitions and no ring animation at all."

- **[high] Mockup: shortcut keys inside primary buttons are invisible** (key-v2.html "Preview post `p`", key-post-edit.html "Save `⌘↵`": `kbd` has `background: var(--surface)` with `color: inherit`). That's white on white in light (1.00:1) and 1.09:1 in dark. DESIGN.md says "every action that has a shortcut shows its key" but only defines `kbd` on neutral surfaces. *Fix:* add `kbd-on-accent` to DESIGN.md components: "transparent background, 1px border in {colors.accent-text} at 60% mixed onto accent, foreground {colors.accent-text}". The text then reads 5.90 / 7.09:1. Fix the two mockups. Hide the key glyph from screen readers (`aria-hidden`) and expose it through `aria-keyshortcuts`, so names read "Preview post", not "Preview post p".

- **[high] WCAG 2.1.4 compliance is a claim, not a spec** (EXPERIENCE.md, Accessibility Floor: "Shortcuts can be turned off or remapped in Settings"). Several things are unstated. Does "off" cover the `g` chords, `?` and `/`? (It must, because they're printable characters.) Where is the setting stored: per browser, per Web App user, or both? What does the remap UI do when two shortcuts collide, and is there a reset? Is the `?` sheet a dialog, and can you remap from it? The palette's "Show stats" carries a `g s` key (key-start.html) that's missing from the shortcut list. *Fix:* "Settings → Keyboard: 'Single-key shortcuts' On (default) / Only when the list or detail has focus / Off. Off disables every unmodified printable-key shortcut, including `g` chords, `?`, `/`, j/k, x, e, c, p; ⌘K/Ctrl+K and Esc stay. Each shortcut can be remapped to a different key or a modifier combination; collisions are refused inline; Reset restores the defaults. Stored per browser (serve) and per user (Web App). The `?` sheet is a modal dialog that lists the current bindings and links to this setting." Add `g s` to the list or remove it from the mockup.

### Medium

- **[medium] Diff semantics are one line in the spec, and the mockup contradicts it** (EXPERIENCE.md, Accessibility Floor: "The diff is a table with line numbers and change type read as text"; key-v2.html uses a `div` grid). The spec leaves open the columns and headers, how the `+`/`−` in the code is handled (otherwise it's read twice: "added, plus …"), how the hunk header row reads, how the commented range is marked, whether the suggestion block uses the same table, and how long lines behave. *Fix:* "Each code box is a `<table>` with a visually hidden caption '<path>, lines 68–73, this PR's change' and visually hidden column headers Old line, New line, Change, Code. The Change cell holds 'added', 'removed' or nothing for context lines, in visually hidden text; the visible `+`/`−` gutter is `aria-hidden`. The hunk header is a full-width row with the `@@` text. Lines the finding is about carry a visually hidden 'commented line' and a visible left marker in {colors.border-strong}. The suggested change uses the same table with the caption 'Suggested change'. Syntax colours, if added, are checked at ≥4.5:1 against surface, diff-add, diff-del and diff-hunk in both themes. The table sits in a `role="region"` scroll container with `tabindex="0"` and an `aria-label` (the caption text); a 'Wrap lines' toggle (remembered) removes horizontal scrolling for people who zoom."

- **[medium] The icon rail is icon-only with unclear glyphs and hides the counts** (EXPERIENCE.md Sidebar; key-v2.html frame 5: ⌕ ◎ ! ≡ ✓). "Names as tooltips and accessible names" passes 4.1.2, but nothing says how the tooltip behaves under 1.4.13 (hoverable, persistent, Esc-dismissable, which collides with Esc = back). The counts ("Needs attention 2") disappear from the rail. The glyph for Needs attention is "!". *Fix:* "Rail items are links with `aria-current="page"` on the active one and an accessible name that includes the count ('Needs attention, 2'). The count shows as a small badge on the icon. Tooltips appear on hover and focus, stay while hovered, dismiss on Esc (top of the Esc order), and are `aria-hidden` (the name is on the link). A rail toggle 'Show labels' (remembered) expands the sidebar to full width at any viewport ≥ 600px. Icons come from one set with real metaphors, not punctuation."

- **[medium] The live-region rules are only partly restated** (EXPERIENCE.md, Accessibility Floor bullet 5). The extension's "Step list and elapsed time are not live" and "Re-attaching announces only the current state" (switching classic↔v2 mid-run) weren't carried over. The filter count isn't debounced, so typing in `/` filter announces on every key. Skeleton tiles have no busy state, and the nav count "…" has no name. The outcomes of x / e-save / c, the drawer's "Preview ready", and posting results don't say whether they're status or alert. *Fix:* add "Not live: the timeline, elapsed time, tiles, nav counts. Tiles region has `aria-busy="true"` while any tile is a skeleton; skeleton blocks are `aria-hidden`, and each tile's name is '<caption>: loading'; the nav count '…' is named 'counting'. Filter results announce 500ms after the last keystroke. Status messages: 'Excluded from post. 1 of 2 included', 'Saved. Marked edited', 'Copied agent prompt', 'Preview ready…', 'Posted…'. Alert: run failed, posting refused, head moved while posting, backend unreachable, sign-in expired. At most one status message per 1.5s, the newest replacing older queued ones, except the final run result."

- **[medium] Command palette: the combobox details are missing, and the sidebar field is a trap** (EXPERIENCE.md Command palette row; Accessibility Floor bullet 7; key-start.html). The spec doesn't say how groups are exposed, how async loading ("owner/repo lists its open PRs" is a network fetch) and empty results are announced, or whether focus returns to the invoker or goes to the new `h1` after an action that switches surface. If the sidebar's "Search or run a command" field is a real `<input>` that opens a dialog on focus, that's a 3.2.1 (On Focus) failure. *Fix:* "The palette is a modal dialog ('Command palette') containing an APG combobox: `input role="combobox" aria-expanded aria-controls aria-activedescendant aria-autocomplete="list"`; the listbox has `role="group"` sections labelled by their group headings; each option's shortcut is in `aria-keyshortcuts` and its status text ('reviewed, 6e53c3e is current') is part of the name. 'Loading open PRs…', 'No matches' and the result count ('5 results') are announced politely after a 300ms debounce. Actions that change the surface move focus to the new `h1`; Esc and Close return focus to the invoker. The sidebar's command field is a `<button>` styled as a field, named 'Search or run a command' with `aria-keyshortcuts="Meta+K Control+K"`; it opens the palette on activation, not on focus."

- **[medium] `g` chords have no timing or feedback rules** (EXPERIENCE.md Interaction Primitives). If `g` times out quickly, a slow typist pressing `g` then `p` gets the post drawer instead of Pre-existing. If it never times out, a stray `g` hijacks the next key. *Fix:* "After `g`, a visible 'g …' indicator appears near the shortcut hints, and the next key completes the chord; the chord is cancelled by Esc, by any non-chord key (which is then swallowed, not run), or after 2s. The timeout is configurable or can be turned off in Settings → Keyboard."

- **[medium] The inline editor needs naming, a quiet preview, and a decision on Markdown** (EXPERIENCE.md Inline editor; DESIGN.md `inline-editor`; key-post-edit.html frame 1). The source shows an uppercase "Wording (Markdown)" div rather than a `<label>`. Nothing says the preview mustn't be a live region; if it is, it will talk on every keystroke. Rendered Markdown can insert `h1`–`h3` into the page's heading outline. The extension's floor says finding text "never renders as rich HTML", which contradicts this preview and isn't reconciled. *Fix:* "The source is a `<textarea>` with a `<label>` 'Comment wording for <finding title>'. The preview is a named region ('Preview'), is not live, and is focusable when it scrolls; rendered headings are demoted to start below the detail's heading level (or rendered as bold text); links in the preview are underlined and inert. Save (⌘/Ctrl+Enter) announces 'Saved. Marked edited' and returns focus to 'Edit wording'. The 'edited' tag is text ('edited'), also included in the row button's name." Record in Foundation that v2 deliberately overrides the extension's plain-text rule for the editor preview only.

- **[medium] The heading and landmark structure in the mockups doesn't match the rule** (EXPERIENCE.md Accessibility Floor bullet 1; key-v2.html uses `h2` for the hero and `h3` for the finding with no `h1`).
