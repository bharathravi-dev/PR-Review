# How AI Code Review Quality Is Benchmarked and Measured (as of Nov 2026)

Research date: 2026-11-25. Most vendor figures are self-reported by the vendor, which also sells the tool being scored. Each finding below says whether it is a methodology fact, a reported number, or a marketing claim. Where a page was read through a summarising fetch tool, the numbers are as extracted. Some vendor result tables exist only as images, so the per-tool figures could not be read and are listed under Gaps.

---

## 1. Vendor-published benchmarks: methodology, scores, criticisms

### Takeaway
Most vendor benchmarks come from one lineage: **50 real bug-fix PRs from 5 OSS repos (Sentry, Cal.com, Grafana, Keycloak, Discourse)**. Greptile built it, and Augment, Propel, Entelligence and Martian's offline track later reused or extended it. The main alternative is Qodo's design, which injects bugs into merged PRs. Each vendor that publishes a benchmark wins its own. Rankings flip between benchmarks because they measure different things (catch rate, F1, resolution rate), use different ground truth, and use different judges. The two most credible yardsticks as of late 2026 are **GitHub's ReviewBench** (Oct 2026: open data, published judge prompt, 96.6% human agreement, though built by GitHub) and **Martian's Code Review Bench** (Feb 2026, MIT-licensed, offline plus online).

### Cited Findings

**Greptile AI Code Review Benchmark (run July 2025)**
- **Data:** 50 **real** bugs (not seeded), 10 per repo, across Sentry (Python), Cal.com (TS), Grafana (Go), Keycloak (Java) and Discourse (Ruby). Each bug was found by tracing a bug-fix PR back to the commit that introduced it. Very large and single-file changes were excluded. — [Greptile benchmarks](https://www.greptile.com/benchmarks.md)
- **Procedure:** The bug-introducing change was re-opened as a fresh PR in a clean fork per tool. Tools ran on hosted plans with default settings, no custom rules and full repo access. Tool versions and runs per case are not stated. — [Greptile benchmarks](https://www.greptile.com/benchmarks.md)
- **Scoring:** A bug was "caught" only if a **line-level comment pointed at the faulty code and explained the impact**. Summary-only mentions did not count. **False positives were not scored**, so the result is recall only. Each bug has a Critical/High/Medium/Low label, but the page does not say how severity was assigned. — [Greptile benchmarks](https://www.greptile.com/benchmarks.md)
- **Reported catch rates:** Greptile 82%, Cursor Bugbot 58%, GitHub Copilot 54%, CodeRabbit 44%, Graphite 6%. — [Greptile benchmarks](https://greptile.com/benchmarks)
- **Internal inconsistencies:** The per-repo case tables give Copilot 26/50 (52%), not the headline 54%. Severity percentages do not reconcile with the case tables either: Greptile Critical is stated as 58% but the tables show 11/15 (73%), and High is stated as 100% but the tables show 14/17 (82%). The page claims to have measured noise, comment quality and latency but reports none of them. — [Greptile benchmarks](https://www.greptile.com/benchmarks.md) (analysis of the page's own tables)
- **Criticism:** "An 82% catch rate is not 82% precision." The small set makes the result sensitive to repo choice and to product updates after July 2025. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/). When Augment re-ran it on the same repos, Greptile scored a 45% F-score. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)

**Augment Code benchmark (published Dec 11 2025, updated Jun 18 2026)**
- **Data:** Starts from the Greptile-derived public dataset (github.com/ai-code-review-evaluation). Augment "expanded and corrected" the golden comments by manually reviewing each PR and checking candidate issues against tool outputs. It also adjusted severity and removed style nits. The corrected data and scripts are said to be in the GitHub org `ai-code-review-evaluations`. — [Augment blog](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)
- **Definitions:** TP = a comment that matches a golden comment. FP = an incorrect or irrelevant comment. FN = a golden comment the tool missed. **The matching procedure (human or LLM judge, which model) is not disclosed.** — [Augment blog](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)
- **Reported results (precision / recall / F):** Augment 65/55/59, Cursor Bugbot 60/41/49, Greptile 45/45/45, Codex Code Review 68/29/41, CodeRabbit 36/43/39, Claude Code 23/51/31, GitHub Copilot 20/34/25. The scatter plot and the table disagree slightly (for example, Augment recall is about 57% vs 55%). — [Augment blog](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)
- **Conflict of interest:** Augment edited the ground truth after seeing tool outputs and then finished first. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)

**Qodo Code Review Benchmark 1.0 (Feb 4 2026)**
- **PR selection:** Merged PRs pulled from active OSS repos via the GitHub API. Filters: 3 or more files changed, 50 to 15,000 changed lines, recently merged, and no later revert or immediate fix-up commit. — [Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)
- **Injection:** Repo best-practice rules were extracted by an agent and validated by humans. Rule violations were injected "using an LLM", along with **1 to 3 functional/logic bugs per PR** (race conditions, resource leaks, error handling). A human double-verification pass followed, and any natural issues it found were added to the ground truth. In total: 100 PRs and 580 issues in TS, Python, JS, C, C#, Rust and Swift (repos include redis, tauri, dify and aspnetcore). Rules were supplied to every tool through AGENTS.md. — [Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)
- **Judge:** An unnamed LLM-as-judge. A **Hit requires both a correct description and the correct file and line location.** Precision is the share of comments that hit, and recall is the share of issues found. No judge validation is reported. — [Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)
- **Reported result:** Qodo F1 60.1%, the best of 8 tools. Qodo says competitors "cluster toward high precision and low recall". Its later claims: 79% precision / 60% recall for the production system, and a 12-point F1 lead over Claude Code Review. These are marketing claims, and the per-tool table is image-only. — [Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/); [Qodo benchmark page](https://qodo.ai/ai-code-review-benchmark/)
- **Data:** PR mapping at https://github.com/agentic-review-benchmarks/benchmark-pr-mapping and dataset at https://huggingface.co/datasets/Qodo/PR-Review-Bench. — [Qodo benchmark page](https://qodo.ai/ai-code-review-benchmark/). DeepSource (Feb 2026) said the injected ground truth was unpublished at that time. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)
- **Criticism:** A GitLab analysis notes that most injected defects are confined to one file, so the benchmark does not target cross-file issues. — [GitLab issue #590266](https://gitlab.com/gitlab-org/gitlab/-/issues/590266) (via search snippet). DeepSource adds that LLM-invented bugs have "no evidence" of matching real defect distributions. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)

**Martian Code Review Bench (launched about Feb 2026, MIT-licensed)**
- **Two tracks:** (1) **Offline**: 50 PRs from the same 5 repos with human-curated golden comments, matched semantically by an LLM judge. (2) **Online**: watches review-bot comments across 200k+ public GitHub PRs, updated daily. "Percentage of comments acted on" is the precision proxy and the count acted on is the recall proxy. The headline metric is F1, with F-beta (F2) also shown. Martian runs each vendor's pipeline itself, and vendors need several hundred public reviews to be listed. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/); [Kilo blog, Mar 5 2026](https://blog.kilo.ai/p/martians-independent-benchmark-tested); leaderboard at https://codereview.withmartian.com/
- **Conflicting golden-issue counts:** Qodo cites 173 golden comments ([Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)). An arXiv paper cites 136 ([arXiv 2606.15689](https://arxiv.org/pdf/2606.15689)). Versions may differ, so check the repo.
- **Martian's own caveats (as relayed by Qodo):** the judge models are not formally calibrated against human annotations, the offline gold set is incomplete and uses older PRs, and true recall is impossible online because the total bug count is unknown. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)
- **Vendors claim #1 on different views or snapshots:** Greptile claims #1 with 60.8% F1 and 76.2% precision ([Greptile](https://www.greptile.com/content-library/greptile-martian-code-review-benchmark), via search snippet). CodeRabbit claims #1 with F1 51.2% and recall 53.5% on the online track. CodeAnt reports F1 51.7% but ranks #3 of 17 ([Atlas aggregator](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)). A snapshot of 6 Oct 2026 reportedly had Cubic first online at 64.9% F1 (search summary, unverified). Kilo and Baz claim #1 among OSS tools and #1 in precision respectively. — [Kilo](https://blog.kilo.ai/p/martians-independent-benchmark-tested); [Baz](https://baz.co/resources/baz-1-in-precision-in-independent-code-review-bench)
- **Criticism:** The offline track shares the 50-PR lineage with Greptile and Augment, so it is "not a fully independent replication". — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/). In the online track, developers edit code for reasons unrelated to the comment, and tools run on different repos and user populations. — [Atlas aggregator](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)

**GitHub ReviewBench (Oct 5 2026, research preview)**
- **Data:** 219 public PRs from 187 repos in 19 languages. Language and repo-size mix are matched to an analysis of 103.9M GitHub PRs, and PR size is deliberately weighted toward multi-file changes. The dataset is public. Site: https://review-bench.ai/ — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Ground truth:** Candidate findings come from human reviewers, issues inferred from the author's follow-up commits, static analysis and several frontier LLMs. They are semantically deduplicated and then validated against one rubric: a finding must be **true, relevant and non-trivial**, whatever its source. Each is labelled by severity (Critical/Medium/Low) and category (Correctness, Security, Reliability, Maintainability, Testing). — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Metrics:** **Grounded P/R/F1** counts only existing gold labels, and grounded recall is the headline. **Augmented P/R/F1** lets the judge credit valid findings outside the gold set, and is a per-system diagnostic only, because its denominator depends on each agent's own output. Fβ is also offered. Judge: Claude Sonnet 5, with the rubric, judge prompt and config published. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Validation:** Senior engineers who did not build the dataset re-labelled every finding and agreed with it **96.6%** of the time. Submissions run in a container, first on a 25-PR set and then on all 219 PRs ×3, with maintainer approval before publication. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Offline-to-online validation:** For a Copilot code review change, ReviewBench predicted the direction of the online A/B result. Online, addressed rate was +8.0%, recall +13.6%, comment volume +61% and cost per review −8.0%. Critical comments were predicted at +227% and came in at +262%. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **COI:** GitHub and Microsoft authors built it and use it on their own product. Only one judge model family is used. Leaderboard entries appear only if they beat the agent's prior score. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)

**Cursor Bugbot: resolution rate (Jan and Apr 2026)**
- **Definition:** At merge time, an LLM decides which flagged bugs the author actually resolved in the final code. Cursor says it spot-checked the judge with PR authors and found "nearly all" classified correctly. Offline, Cursor uses **BugBench**, a curated set of real diffs with human-annotated bugs (size not disclosed). Over about 40 experiments, resolution rate rose from 52% to over 70% and bugs flagged per run from 0.4 to 0.7. — [Cursor, Building a better Bugbot, Jan 15 2026](https://cursor.com/blog/building-bugbot)
- **Cross-vendor table (Apr 8 2026, measured by Cursor on public repos with an LLM judge):** Bugbot 78.13% (50,310 PRs), Greptile 63.49% (11,419), CodeRabbit 48.96% (33,487), Copilot 46.69% (24,336), Codex 45.07% (19,384), Gemini Code Assist 30.93% (21,031). No time window, judge accuracy or confidence intervals are given. — [Cursor, Bugbot learning](https://cursor.com/blog/bugbot-learning)
- **Caveat:** "Addressed" does not prove the comment was correct or that the fix came from it. A tool that comments less, and only on obvious issues, can inflate this rate. — [Cursor, Bugbot learning](https://cursor.com/blog/bugbot-learning) (caveats as extracted)

**Others**
- **Macroscope:** 118 bugs across 45 repos and 8 languages. Reported detection: Macroscope 48%, CodeRabbit 46%, Bugbot 42%, Greptile 24%, Graphite Diamond 18%. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks); [Macroscope blog mirror](https://hn.jakechampion.name/reader/https://blog.macroscope.com/blog/code-review-benchmark)
- **Entelligence:** 67 bugs on Greptile's 5 repos, ground truth from a 3-LLM majority vote, 47.2% F1. **Propel:** 64% F1 on Augment's dataset. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)
- **CodeRabbit:** No reusable public benchmark. It describes an internal "hard set" of 25 difficult PRs seeded with known error patterns, used for regression testing when models or prompts change (and therefore for tuning). — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/). Bito reports 69.5% coverage vs CodeRabbit's 65.8% on its own 65-issue set. — [Atlas aggregator](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)
- **Graphite (Diamond):** Uses acceptance rate as its primary metric internally, plus "matched comment rate" (a recall proxy) and "unmatched comment rate" (a noise proxy) for offline model evaluation. — [search summary of Graphite and Braintrust sources](https://www.braintrust.dev/customers/graphite). Graphite was reportedly folded into Cursor after a Dec 2025 acquisition. — [Atlas aggregator](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/) (unverified)
- **DeepSource:** A security-only benchmark of 165 CVEs from OpenSSF, released as JSONL, with an Opus 4.5 judge blinded to tool names. DeepSource discloses its own conflict ("skin in this game"). — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)
- **Meta-critique:** "Every AI code review vendor benchmarks itself, and wins." DeepSource recommends real ground truth, versioned public datasets, a judge blinded to tool identity, at least 100 entries (fewer can swing scores by 10+ points), published raw outputs and verdicts, and a community-run benchmark. — [DeepSource, Feb 26 2026](https://deepsource.com/blog/ai-code-review-benchmarks)

### Inferences
- The same tool can score 82% (Greptile's catch rate), 45% F (Augment), or #1 on Martian, depending on who built the benchmark. The variance comes from **ground-truth construction and the metric**, not only from tool quality. Comparisons are only meaningful within one benchmark, one snapshot and one metric.
- The Greptile/Augment/Martian 50-PR set is old, public and heavily discussed, so it is probably contaminated by vendor tuning. Use it for comparability with published numbers, not as a held-out test.
- ReviewBench is the most methodologically complete public design: multi-source ground truth, grounded vs augmented metrics, a published judge with human validation, runs ×3, and an offline-to-online correlation check. It is the best template to copy, despite the COI.

### Gaps
- Per-tool precision/recall tables for Qodo, Martian and Macroscope are image-only or only on live leaderboards, so they could not be extracted reliably. Live Martian numbers could not be fetched (the page is JS-rendered).
- The Martian judge model and exact matching prompt were not confirmed from the repo.
- No source independently replicated any vendor benchmark on a fresh PR population.
- Graphite did not publish a cross-tool benchmark of its own. Its 52% acceptance figure is speaker-reported (see Q3).

## 2. Academic and open datasets, tasks, metrics, leaderboards

### Takeaway
Academic evaluation has moved from **comment generation scored by BLEU against one human reference** (CodeReviewer, 2022) to **PR-level defect detection with repository context, scored as recall, precision or F1 by a validated LLM judge** (SWR-Bench, SWE-PRBench, AACR-Bench, CR-Bench-v2, ReviewBench). Every 2025–26 benchmark reports low absolute numbers: frontier systems detect roughly 15–33% of known issues. Several report that adding more raw context *hurts*.

### Cited Findings
- **Microsoft CodeReviewer (ESEC/FSE 2022):** A pre-trained model plus a dataset mined from GitHub review data. It covers three tasks: diff quality estimation, review comment generation, and code refinement. Comment generation is scored with **BLEU-4**. The authors concede that review comments are "diverse and non-unique" and add human ratings of informativeness and relevance. — [arXiv 2203.09095](https://arxiv.org/pdf/2203.09095)
- **Noisy references:** A 2025 audit reportedly found only 64% of CodeReviewer comments valid. — [Atlas aggregator](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/) (original paper not checked)
- **CRScore (NAACL 2025):** A reference-free metric. It generates "pseudo-references" (claims, implications, code smells) from the diff and scores a review for conciseness, comprehensiveness and relevance using semantic similarity. Its motivation is that review is one-to-many, so reference-based metrics fail. Spearman correlation with humans is 0.54, on a released corpus of about 2.9k human-scored reviews. — [ACL Anthology](https://aclanthology.org/2025.naacl-long.457); [arXiv 2409.19801](https://arxiv.org/abs/2409.19801v1)
- **SWR-Bench (Sep 2025, revised Jun 2026):** 1,000 manually verified GitHub PRs with full project context. The task is generating review comments. An LLM judge checks whether structured ground-truth issues are covered, with about 90% agreement with humans. The metric is F1. Tools and LLMs "underperform" (best F1 about 19.4%, per the aggregator). Aggregating multiple reviews raises F1 by up to 43.67%. — [arXiv 2509.01494](https://arxiv.org/abs/2509.01494); [Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)
- **ContextCRBench (Nov 2025, ByteDance-linked):** 67,910 entries that link line-level review comments to hunks, with issue and PR descriptions and enclosing function or class context. Three tasks: hunk-level quality assessment, line-level defect localisation, and comment generation. It was used as a reward signal for a self-evolving reviewer (61.98% relative improvement). — [arXiv 2511.07017](https://arxiv.org/abs/2511.07017v1)
- **AACR-Bench (Jan 2026):** 200 PRs and 1,505 review comments from 50 repos in 10 languages, with repository-level and cross-file context. Annotation combines model-generated and human-reviewed comments, which the authors say raises defect coverage by 285% over human comments alone. The authors note ContextCRBench is limited to file-level context. — [arXiv 2601.19494](https://arxiv.org/html/2601.19494)
- **SWE-PRBench (Mar 2026):** 350 PRs selected from 700 by a Repository Quality Score. Ground truth is the issues human reviewers flagged on merged PRs. Three frozen context configs: A (diff), B (diff plus file content), and C (full context: AST function context, import graph, tests). The LLM judge is validated at **κ = 0.75**. Eight frontier models detect **15–31%** of human-flagged issues. The top four are statistically indistinguishable (mean 0.147–0.153). **All models degrade monotonically from A to C**, and a structured 2k-token diff-plus-summary prompt beats 2.5k tokens of full context. Data and harness are released. — [arXiv 2603.26130](https://arxiv.org/abs/2603.26130)
- **CR-Bench-v2 (Nov 2026):** Recasts SWE-bench issues as PR-review tasks with full repo context. Each defect is tied to its originating PR, and the set is filtered to defects a reviewer could plausibly catch. 584 instances, plus a 174-instance **CR-Bench-Verified** subset from SWE-bench Verified. Each instance has the PR, the known defect, the ground-truth fix, and category/impact/severity labels. Metrics: **Known-Defect Detection Rate (KDDR)** and **Usefulness Rate** (share of comments that are actionable), scored by 3 independent LLM judges. The best systems reach about 33% KDDR, and Gemini Code Assist 8.1%. It explicitly criticises text-similarity metrics and noisy human-comment ground truth. — [arXiv 2611.02566](https://arxiv.org/abs/2611.02566)
- **Other 2026 work found:** MCR-Bench ([arXiv 2608.27442](https://arxiv.org/pdf/2608.27442), "static to dynamic" review); SWE-Review ([arXiv 2607.06065](https://arxiv.org/pdf/2607.06065)); Adversarial Review, which evaluates on a 100-PR subset of SWE-PRBench ([arXiv 2608.18167](https://arxiv.org/pdf/2608.18167)); "Bigger Isn't Always Better", which uses Martian's offline track for external validation, where Haiku 4.5 scored F1 36.4% vs Sonnet 4.6 at 27.1% because Sonnet was more conservative on large diffs ([arXiv 2606.15689](https://arxiv.org/pdf/2606.15689)). An AIDev in-the-wild study of 3,109 PRs found 12 of 13 agents below 60% signal ([Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/), citing arXiv 2604.03196). A 2026 survey of 99 code-review benchmark papers calls the field's metrics "immature" ([Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)).
- **Leaderboards:** ReviewBench (https://review-bench.ai/) and Martian (https://codereview.withmartian.com/) are the active public tool leaderboards. Academic benchmarks mostly publish static tables in their papers.

### Inferences
- The task taxonomy now settles on three levels: (a) **defect detection** (did the reviewer find the known bug: recall/KDDR), (b) **comment precision and usefulness** (is each comment valid and actionable), and (c) **comment text quality** (CRScore-like). BLEU-style metrics are effectively deprecated for evaluating review tools.
- SWE-PRBench's finding that more context hurts means context-retrieval features should be ablated, not assumed to help.
- CR-Bench-Verified and SWE-PRBench are the easiest open sets for an OSS team to run without vendor bias. Both release a harness, but both carry contamination risk because the PRs predate current model cutoffs.

### Gaps
- Exact BLEU scores and the dataset size for CodeReviewer were not extracted. The 64% validity audit was not read in its primary source.
- The models in SWE-PRBench and the agents in CR-Bench-v2 are not named in the abstracts. The full papers were not read.
- The "CodeReviewBench" (30 PRs, 95 bugs, P/R/F1 plus cost per PR) appears only in Qodo's glossary. Its primary source was not found.

## 3. Operational (production) metrics and how they are instrumented

### Takeaway
Production quality is measured mainly by **whether a comment led to a code change before merge**. Vendors call this addressed, resolved, accepted or acted-on rate, and it is detected by an LLM judge comparing the comment with later commits, or by thread resolution. It is paired with **comment volume**, **explicit feedback** (reactions and replies), **cost per review**, and **PR cycle time**. Each is a proxy. Resolution rate rewards silence, and reactions are sparse and biased.

### Cited Findings
- **Resolution rate (Cursor):** At merge, an LLM judges whether each flagged bug was fixed in the final code. It is reported alongside bugs flagged per run (0.4→0.7) and resolved bugs per PR (about 0.2→0.5). Learning signals are 👍/👎 reactions, replies explaining errors, and human comments flagging bugs Bugbot missed. These become candidate rules that are promoted or disabled depending on later signal (110k repos, 44k rules). — [Cursor Jan 2026](https://cursor.com/blog/building-bugbot); [Cursor Apr 2026](https://cursor.com/blog/bugbot-learning)
- **Addressed rate (GitHub Copilot):** Used as the online precision metric, alongside recall, comment volume, cost per review and count of critical-severity comments, all measured in online A/B tests. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Acted-on rate (Martian online):** Percentage of comments acted on is the precision proxy and the count acted on is the recall proxy. Detection uses code edits after the comment. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/); [Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)
- **Acceptance rate (Graphite):** The primary metric. Diamond comments reportedly had about 52% acceptance vs about 45–50% for human comments, with downvotes under 4%. These figures are speaker-reported at AI Engineer 2025, with no denominator or window given, and a downvote rate is not a false-positive rate. The dashboard shows issues found, issues accepted and acceptance rate by category. Graphite's claim of a 5–8% false-positive rate is unsourced marketing. — [search summary: AI Engineer talk](https://www.ai.engineer/talks/TswQeKftnaw-ai-powered-entomology-lessons-from-millions-ai); [Graphite FP guide](https://graphite.com/guides/ai-code-review-false-positives)
- **Atlassian RovoDev Code Reviewer (ICSE-SEIP 2026, peer-reviewed industrial study):** A year-long deployment across more than 1,900 repos and 54k+ comments. **Code resolution rate was 38.70%, vs 44.45% for human comments** (12.9% relatively lower). Median PR cycle time fell 30.8%. Readability, bug and maintainability comments are resolved most often. — [arXiv 2601.01129](https://arxiv.org/html/2601.01129v1); [Atlassian blog](https://www.atlassian.com/blog/atlassian-engineering/atlassian-rovo-dev-research-what-types-of-code-review-comments-do-developers-most-frequently-resolve)
- **Microsoft internal AI reviewer (Jul 2025):** Covers more than 90% of PRs (over 600k/month). Early-adopter repos (5,000 onboarded) saw a **10–20% improvement in median PR completion time**. No comment-resolution rate was published. — [Microsoft Engineering blog](https://devblogs.microsoft.com/engineering-at-microsoft/enhancing-code-quality-at-scale-with-ai-powered-code-reviews/)
- **Counter-evidence on latency:** An industrial study of automated review found 73.8% of automated comments labelled resolved, but average PR closure time *rose* from 5h52m to 8h20m. — [arXiv 2412.18531, Automated Code Review in Practice](https://arxiv.org/html/2412.18531v2)
- **Google (earlier work):** Measured ML-suggested edits for resolving reviewer comments by reviewer acceptance of suggested edits. — [Google Research blog](https://research.google/blog/resolving-code-review-comments-with-ml/) (details not extracted)

### Inferences
- **A minimal production metric set for an OSS tool:** (1) addressed rate, judged by LLM or diff-overlap on commits after the comment and before merge; (2) comments per PR and the share of PRs with zero comments; (3) explicit 👍/👎 reactions and reply sentiment; (4) suggestion-apply rate, i.e. GitHub "commit suggestion" events; (5) thread-resolved rate (weak, because authors bulk-resolve); (6) time to first review and p50/p95 latency; (7) tokens and USD per PR; (8) severity mix of comments. Always report addressed rate together with volume, because one can be gamed against the other.
- The human baseline for resolution is about 44% (Atlassian), so a tool above roughly 40–50% addressed rate is competitive with human reviewers on this proxy. Cursor's 78% figure probably reflects a more selective commenting policy.

### Gaps
- No source gives a validated, public implementation of "addressed" detection, meaning judge accuracy against human labels, beyond Cursor's informal spot-check.
- No vendor publishes developer-satisfaction survey methodology in comparable form.
- No independent data was found on suggestion-apply rates across tools.

## 4. Recommended evaluation design for a new tool (and pitfalls)

### Takeaway
Build a **small, versioned, two-part benchmark**. (a) About 50–100 **real historical bug-introducing PRs**: trace bug-fix commits back to their origin, preferably PRs merged after the model cutoff, plus an open set such as CR-Bench-Verified or SWE-PRBench. (b) Optionally, an **injected-bug** set for controlled regression tests. Score with **grounded precision and recall**, where a match requires the same defect and a location within a line tolerance, judged by a rubric-driven LLM judge that is validated against a human-labelled sample (κ or % agreement). Run each PR ×3, publish per-PR outputs, and treat unmatched-but-valid findings as a separate "augmented" diagnostic. Then confirm offline gains against an online addressed rate.

### Cited Findings
- **Ground-truth options and trade-offs:** Historical comments are natural but incomplete, and injected defects are controlled but synthetic. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/). Real ground truth (bug-fix commits, CVEs, human-validated defects) is preferred. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)
- **Construction recipes to copy:** Greptile's trace-back (bug-fix PR → commit that introduced the bug → re-open as a fresh PR in a clean fork) ([Greptile](https://www.greptile.com/benchmarks.md)). Qodo's filters (3+ files, 50–15k LOC, no revert or follow-up fix) and supplying repo rules through AGENTS.md ([Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)). ReviewBench's multi-source candidates (human comments, the author's follow-up commits, static analysis, several LLMs) → deduplicate → validate with a "true, relevant, non-trivial" rubric, with severity and category labels ([GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)). CR-Bench-v2's approach of recasting SWE-bench defects as review tasks ([arXiv 2611.02566](https://arxiv.org/abs/2611.02566)).
- **Match rules:** Greptile requires a line-level comment that points at the faulty code and explains the impact, with summaries excluded ([Greptile](https://www.greptile.com/benchmarks.md)). Qodo requires a correct description plus the correct file and line ([Qodo blog](https://www.qodo.ai/blog/how-we-built-a-real-world-benchmark-for-ai-code-review/)). Martian and SWR-Bench use semantic LLM matching (issue coverage), with SWR-Bench at about 90% human agreement ([arXiv 2509.01494](https://arxiv.org/abs/2509.01494)). SWE-PRBench validates its judge at κ = 0.75 ([arXiv 2603.26130](https://arxiv.org/abs/2603.26130)), and ReviewBench reports 96.6% agreement ([GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)).
- **Grounded vs augmented scoring:** Report grounded recall as the headline. Augmented metrics, which credit valid findings outside the gold set, are diagnostics only, because their denominators differ per system. — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/)
- **Checklist (Qodo):** The task must be actual review. Give full-PR, cross-file inputs. Disclose where ground truth came from. Give every tool identical inputs. Use standard P/R definitions and label proxies as proxies. Freeze defaults. Publish per-PR outputs. Validate the judge. Run repeatedly and report uncertainty. State what the benchmark cannot prove. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)
- **Judge hygiene:** Blind the judge to tool identity ([DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks)). Use a judge from a different provider than the generator, and spot-check it against humans in your domain ([Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)). Use multiple judges (3 in [CR-Bench-v2](https://arxiv.org/abs/2611.02566)).
- **Pitfalls:**
  - **Leakage and contamination:** Public PRs predate model training. Use time-split PRs merged after the cutoff (the SWE-rebench approach). — [Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)
  - **Shared lineage:** The Greptile/Augment/Martian sets share one origin. — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)
  - **Overfitting:** Tuning on evaluation failures contaminates results (CodeRabbit's hard set). — [Qodo glossary](https://www.qodo.ai/glossary/what-is-ai-code-review-benchmarks/)
  - **Post-hoc gold edits:** Augment edited the gold set after seeing tool outputs. — [Augment blog](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)
  - **Small samples:** Under 100 items, a few edge cases can swing scores by 10+ points. — [DeepSource](https://deepsource.com/blog/ai-code-review-benchmarks). Close scores can be statistical ties (SWE-PRBench's top 4). — [arXiv 2603.26130](https://arxiv.org/abs/2603.26130)
  - **Metric mixing:** Catch rate, F1, resolution rate and coverage measure different things and should not be ranked together. — [Atlas](https://laoujin.github.io/Atlas/research/2026-06-09-ai-assisted-code-review-in-2026-landscape-tools-evidence-and-limits/evaluation-rubrics-and-benchmarks/)
  - **Arithmetic errors in published tables:** See the Greptile inconsistencies under Q1. — [Greptile](https://www.greptile.com/benchmarks.md)
- **Offline-to-online check:** ReviewBench showed that offline deltas predicted the direction of online A/B deltas (addressed +8%, recall +13.6%). — [GitHub blog](https://github.blog/ai-and-ml/reviewbench-an-open-benchmark-for-ai-code-review/). Cursor runs online resolution rate together with the offline BugBench for every experiment. — [Cursor](https://cursor.com/blog/building-bugbot)

### Inferences (concrete plan for the OSS team)
1. **Comparable external runs:** Run the tool on (a) the public 50-PR Greptile/Augment set (github.com/ai-code-review-evaluations), so results line up with published vendor numbers, (b) CR-Bench-Verified (174) and/or SWE-PRBench, and (c) ReviewBench through its submission flow, the only public leaderboard with a validated judge.
2. **Private held-out set:** Mine 50–100 bug-fix PRs merged after the model cutoff from repos the team uses. Run `git log --grep fix`, then blame to find the introducing commit, and re-open it as a PR on a fork. Label severity and category, have two humans adjudicate, and record inter-annotator agreement. Keep the set frozen and versioned, and never tune on it. Keep a separate dev split.
3. **Scoring:** For each gold issue, the tool is credited if any comment (a) refers to the same file within ±N lines (for example N = 5, or the same hunk) **and** (b) an LLM judge with a published rubric says it describes the same root cause. Line overlap alone misses findings made at a different line, and a judge alone hallucinates matches. Unmatched comments go to a judge-plus-human "valid extra" bucket for augmented precision. Report grounded P/R/F1 (and F2 if the product is recall-first), per-severity recall, comments per PR, cost per PR and latency, as mean ± stdev over 3 runs.
4. **Judge validation:** Hand-label about 100 (comment, gold) pairs. Report κ against the judge and target ≥0.7 (SWE-PRBench reached 0.75). Use a judge model from a different family than the reviewer model, blind to the tool's name.
5. **Ablate context:** Given SWE-PRBench's finding, test diff-only vs retrieved context.
6. **Production telemetry:** Addressed rate (LLM-judged against later commits up to merge), 👍/👎 reactions, suggestion-commit events, thread resolution and comments per PR. Compare against the ~44% human resolution baseline from Atlassian.

### Gaps
- No published study compares line-overlap matching with LLM-judge matching head to head for review findings. The hybrid rule above is a recommendation, not a sourced result.
- No public guidance was found on the minimum benchmark size needed for a given confidence interval in code review. The "at least 100 items" advice is DeepSource's opinion.
- Whether ReviewBench accepts submissions from non-commercial OSS tools, and at what cost (agents bring their own model key), was not confirmed.
